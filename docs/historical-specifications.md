# Original PRD (historical source)

Here’s a build-ready PRD for the MVP, scoped so an engineer or coding agent can implement the whole thing in one pass against the existing `blog_posts/` corpus.

# Product Requirements Document
## Personal Writing Style Fingerprint MVP

### 1. Overview

Build a local ML system that learns a high-fidelity fingerprint of the user's historical writing style from Markdown files already present in:

```text
blog_posts/
```

The system must:

1. Ingest and preprocess all Markdown blog posts in `blog_posts/`.
2. Build a persistent personal writing-style reference model.
3. Score arbitrary new text for compatibility with the learned writing style.
4. Provide interpretable explanations of why a piece of writing does or does not match.
5. Identify specific sentences or passages responsible for stylistic mismatch.
6. Retrieve historical passages that are stylistically similar to the candidate text.
7. Support reproducible evaluation despite the small number of source documents.
8. Run locally and persist all generated models, embeddings, features, indexes, and metadata.

The MVP should be implemented end-to-end in one pass. It should not require manual labeling beyond the existing blog corpus.

---

# 2. Product Goal

The primary user question is:

> "How closely does this text match my historical pre-AI writing style, and what specifically does or does not sound like me?"

This is an authorship-verification / style-compatibility problem rather than a conventional multiclass classification problem.

The system should output a compatibility score rather than claiming definitive authorship.

Example:

```text
Style compatibility: 87 / 100
Evidence strength: High

Strong matches:
- Sentence-length distribution closely matches historical writing.
- Function-word usage is strongly consistent.
- Parenthetical and punctuation patterns are characteristic.
- Authorship embeddings align closely with 5 of 6 historical posts.

Largest mismatches:
- Paragraphs are substantially shorter than the historical baseline.
- Passive voice is unusually frequent.
- Sentences 12–14 account for most of the embedding mismatch.
```

---

# 3. Non-Goals

The MVP will not:

- Determine legal or forensic authorship.
- Claim a calibrated probability that the user wrote a document.
- Train a large language model from scratch.
- Generate text in the user's style.
- Attempt to detect whether text was generated by AI.
- Fine-tune a transformer directly on a sparse positive dataset unless evaluation clearly justifies it.
- Depend on cloud inference APIs.
- Require a GPU, although GPU acceleration should be supported automatically when available.
- Treat chunks from the same source document as independent validation samples.

## 6.1 Source

```text

```

should be recursively discovered.

Each Markdown file represents one independent historical document.

## 6.2 Markdown preprocessing

Strip content unlikely to represent prose style:

- YAML front matter
- HTML tags
- fenced code blocks

- bare URLs
- navigation boilerplate

- paragraphs
- punctuation
- sentence boundaries
- list-item prose

Code blocks must not contribute to style embeddings or stylometry.

Store both:

```text

```

for every document.

# 9. Authorship Embedding Model

## 9.1 Primary representation

Use a modern authorship-specific embedding model capable of multi-vector / late-interaction comparison.

Preferred default:

```text
LUAR-MUD-MV-Qwen
```

or the best compatible current LUAR-style multi-vector checkpoint available at implementation time.

Embeddings must remain passage-level.

Do not average all historical writing into a single vector.

Reference structure:

```python
reference_bank = {
    document_id: [
        embedding_chunk_1,
        embedding_chunk_2,
        ...
    ]
}
```

---

## 9.2 Similarity

Compute candidate-to-reference similarity using late interaction.

For candidate vectors:

```text
C = {c1, c2, ..., cm}
```

and reference-document vectors:

```text
R = {r1, r2, ..., rn}
```

calculate a symmetric MaxSim-style score.

Conceptually:

```text
candidate_to_reference =
mean_i max_j cosine(ci, rj)

reference_to_candidate =
mean_j max_i cosine(rj, ci)

score =
(candidate_to_reference + reference_to_candidate) / 2
```

Retain document-level and corpus-level score distributions.

Derived features should include:

```text
mean reference similarity
median reference similarity
minimum
maximum
std deviation
p10
p25
p75
p90
best matching document
worst matching document
fraction of chunks above threshold
fraction of chunks below threshold
candidate chunk similarity mean
candidate chunk similarity variance
```

# 10. Stylometric Features

Create an interpretable feature vector for every document and passage.

Target:

```text
100–300 features
```

Feature categories should include:

### Length and rhythm

- sentence length mean
- sentence length median
- sentence length standard deviation
- sentence length skew
- paragraph length mean
- paragraph length variance
- words per paragraph
- sentences per paragraph

### Word-level behavior

- average word length
- word-length histogram
- lexical density
- type-token ratio variants
- hapax rate
- long-word rate
- short-word rate

### Function words

Normalized frequency of common:

- articles
- pronouns
- conjunctions
- prepositions
- auxiliaries
- determiners

### Punctuation

Normalized frequency of:

```text
,
.
;
:
—
-
(...)
?
!
"..."
```

Include punctuation sequence patterns where useful.

### Syntax proxies

Where feasible:

- POS frequencies
- POS bigrams
- POS trigrams
- subordinate clause markers
- coordinating conjunction rate
- passive-construction proxy
- sentence-initial conjunction rate

### Voice and discourse

- first-person singular frequency
- first-person plural frequency
- second-person frequency
- rhetorical-question frequency
- contraction frequency
- parenthetical frequency
- transition-word frequency
- hedging terms
- intensifiers
- discourse markers

### Structural habits

- heading frequency
- list frequency
- quote usage
- one-sentence paragraph rate
- paragraph-opening patterns

Every feature must have:

```text
candidate value
historical mean
historical median
historical standard deviation
robust z-score
historical percentile
```

when statistically meaningful.

# 11. Character-Level Model

Build a traditional authorship baseline using:

```text
character 3-grams
character 4-grams
character 5-grams
```

with TF-IDF.

Train an appropriate linear classifier or similarity model.

Preferred baseline:

```text
TF-IDF + linear SVM
```

Because the positive corpus is small, training examples may be passage-level, but evaluation must remain document-grouped.

The char model should contribute:

```text
decision-function score
distance to positive style profile
nearest reference score
```

to the final verifier.

---

# 12. Semantic Similarity Control

Use a general-purpose semantic embedding model independently of the authorship model.

Purpose:

Detect whether a high style score may merely reflect topic similarity.

This signal should not dominate the verifier.

Calculate:

```text
semantic similarity to historical corpus
semantic similarity to closest historical document
style-to-semantic similarity ratio
style similarity residual after semantic similarity
```

This enables identifying cases such as:

```text
same topic + different style
different topic + same style
```

---

# 13. Comparison Feature Layer

Never feed raw high-dimensional authorship embeddings directly into the final tree model for the MVP.

Instead, derive interpretable comparison features.

Input to the final verifier should resemble:

```text
authorship embedding comparisons       ~20–40
stylometric distances                  ~100–300
char-ngram signals                     ~5–20
semantic-control signals               ~5–15
length / evidence features             ~5–10
```

Total target:

```text
~150–350 tabular features
```

# 18. Explainability Layer

The explainer is a first-class product requirement.

It must provide four explanation types.

---

## 18.1 Stylometric deviation explanation

Return the largest interpretable deviations.

Example:

```text
Paragraph length
Historical median: 91 words
Candidate median: 54 words
Deviation: -1.8 SD

Semicolon frequency
Historical: 2.6 / 1,000 words
Candidate: 0.2 / 1,000 words
Deviation: -2.1 SD
```

Return both:

```text
strongest matches
largest mismatches
```

---

## 18.2 Verifier feature attribution

Use SHAP or equivalent feature attribution on the final tabular model.

Map technical features into user-readable names.

Do not expose unexplained raw model dimensions.

Example:

```text
Positive contributors:
+ embedding median similarity
+ function-word distance
+ parenthetical rate
+ sentence-length variance

Negative contributors:
- paragraph-length mismatch
- passive-voice rate
- character 4-gram margin
```

---

## 18.3 Sentence-level deletion analysis

For sufficiently long candidate text:

1. Score the full candidate.
2. Remove each sentence individually.
3. Re-score.
4. Calculate:

```text
delta_i = score_without_sentence_i - original_score
```

Large positive delta means the removed sentence was stylistically inconsistent.

For long documents, optimize by first evaluating paragraph/chunk-level attribution and only perform sentence deletion within suspicious passages.

Return:

```python
[
    {
        "sentence": "...",
        "index": 17,
        "original_score": 0.81,
        "score_without": 0.88,
        "delta": +0.07
    }
]
```

---

## 18.4 Historical analogue retrieval

For each candidate passage, retrieve stylistically closest historical passages.

Return:

```text
source document
source passage
similarity score
excerpt
```

Also identify candidate passages with no close historical analogue.

# 35. Key Design Principles

The implementation should preserve the following principles.

### Independent documents are the real sample size

Source documents remain independent examples regardless of how many chunks are generated from them.

### Preserve multi-vector information

Do not compress the historical corpus into one averaged embedding.

### Learn comparison functions, not identity vectors

The final model should operate on candidate-vs-reference similarity features rather than trying to memorize a single representation of the user.

### Keep content separate from style

Semantic similarity should act as a nuisance/control variable rather than a primary authorship signal.

### Interpretability is part of the model

Stylometry, passage retrieval, feature attribution, and deletion tests are required outputs, not optional visualization work.

### Scores represent compatibility

Until sufficient negative-author calibration data exists, output should be interpreted as:

```text
"compatibility with the historical style fingerprint"
```

rather than:

```text
"probability this person wrote the text"
```

# Design background (historical source)

Yes. Given your actual goal, I’d build this as a **personal style-verification ensemble** with a modern authorship embedding model as the main signal, then use an interpretable tabular verifier on top.

The biggest architectural change from my previous answer is: **do not reduce your writing to one embedding centroid**. Recent authorship work is moving toward late interaction / multi-vector scoring, where multiple pieces of an author’s writing remain separately represented. A 2026 study found that the scoring mechanism alone can produce very large differences in authorship-attribution performance, with late-interaction approaches behaving substantially differently from mean pooling. [arXiv](https://arxiv.org/abs/2605.19908?utm_source=chatgpt.com)

A particularly interesting current starting point is `rrivera1849/LUAR-MUD-MV-Qwen`. It is a new 0.6B Qwen3-based successor to LUAR, outputs one 512-d vector per text in an author's “episode,” and uses ColBERT-style MaxSim rather than collapsing everything immediately. Its model card reports MRR 0.6564 versus 0.5706 for the released original LUAR on the MUD benchmark. It was trained on 1.07M Reddit authors, so I would treat those numbers as evidence that the architecture is promising—not evidence that it'll automatically work that well on your blogs. [huggingface.co](https://huggingface.co/rrivera1849/LUAR-MUD-MV-Qwen?utm_source=chatgpt.com)

The system I'd build looks roughly like this:

```text
                 ┌─────────────────────────────┐
                 │ Your pre-AI reference corpus│
                 │ blogs + old writing samples │
                 └──────────────┬──────────────┘
                                │
                         document-preserving
                              chunking
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
       Authorship encoder   Stylometry       char n-grams
       LUAR-MV / PLI       feature vector     TF-IDF/SVM
              │                 │                 │
         multi-vector        interpretable       lexical/
         style scores          style stats       microstyle
              └────────────┬────┴───────┬─────────┘
                           │
                   comparison features
                           │
                LightGBM / CatBoost /
               calibrated logistic model
                           │
                    MATCH VERIFIER
                           │
              ┌────────────┴─────────────┐
              │                          │
        match/confidence             explainer
```

I would implement it in roughly these pieces:

1. **Build the corpus correctly.** Your blog posts are usable, particularly if substantial, but a sparse inventory remains a small statistical sample. Finding more old `.txt`, Markdown, forum posts, essays, etc. is extremely valuable. I'd care more about increasing the number of *independently written documents* than simply generating thousands of overlapping chunks from a small set of documents.

Keep document identity, date, genre and topic as metadata. If you have 50 chunks from one blog post, those are not 50 independent examples.

Also decide what you're fingerprinting. If this is specifically “my long-form blog voice,” don't indiscriminately mix Slack messages, technical documentation, emails and blog prose into one positive class. Either exclude those or build separate profiles such as `blog`, `technical`, `casual`, etc.

2. **Use multiple short passages per document rather than a single huge embedding.** This fits the new LUAR-MV design nicely. That model was trained on episodes containing multiple short texts and explicitly retains one vector per text before doing MaxSim comparison. [Hugging Face](https://huggingface.co/rrivera1849/LUAR-MUD-MV-Qwen?utm_source=chatgpt.com)

For a blog post I'd probably produce something like 8–20 natural segments: paragraphs or groups of sentences rather than arbitrary overlapping token windows.

So instead of:

```python
my_style = mean(embed(all_my_blog_posts))
score = cosine(embed(candidate), my_style)
```

you'd effectively have:

```python
references = [
    [r1_1, r1_2, ..., r1_n],   # blog 1
    [r2_1, r2_2, ..., r2_n],   # blog 2
    ...
]

candidate = [c1, c2, ..., cm]

scores = [
    symmetric_maxsim(candidate, ref)
    for ref in references
]
```

Then retain the whole distribution:

```text
median score
mean score
minimum
maximum
10/25/75/90th percentiles
best reference
worst reference
variance across references
fraction of candidate chunks above threshold
fraction strongly below threshold
```

Those are much better downstream features than “here are 512 opaque embedding dimensions.”

3. **Run more than one representation channel.** My initial experiment would use LUAR-MUD-MV-Qwen as the principal model, original LUAR-MUD as a stable baseline, and one of the new ModernBERT deep-stylometry late-interaction checkpoints as an experimental second encoder. The 2026 HALvest work also found advantages from keeping sequences of representations and matching them with late interaction rather than always producing a single document vector. [Deep Learn](https://deeplearn.org/arxiv/759274/halvest-contrastive%3A-retrieval-like-authorship-attribution-with-patch-level-late-interaction?utm_source=chatgpt.com)

I'd also benchmark CISR because it was deliberately designed to reduce the “same author = same topic” shortcut. That distinction matters enormously for you: your model should ideally recognize your style when you're writing about something you've never written about before. [ACL Anthology](https://aclanthology.org/2022.repl4nlp-1.26/?utm_source=chatgpt.com)

I would *not* use a normal semantic embedding model as the primary style representation. But I would calculate semantic embeddings as an auxiliary feature precisely so we can detect topic contamination.

For example:

```text
Candidate             Semantic similarity    Style similarity
--------------------------------------------------------------
same topic, other guy       HIGH                  LOW
new topic, you              LOW                   HIGH
same topic, you             HIGH                  HIGH
```

The first two rows are extraordinarily useful validation cases.

4. **Add explicit stylometry.** I'd probably create 100–300 interpretable features. This is crucial for the explainer.

Things like sentence length mean/SD/skew, paragraph lengths, punctuation frequencies, function-word frequencies, POS n-grams, contractions, passive constructions, transition words, pronouns, determiners, lexical density, type/token measures, word-length distribution, clause depth, parentheses, colon/semicolon/em-dash usage, question frequency, sentence-initial conjunctions, capitalization, headings, bullet habits, rhetorical-question frequency, and so forth.

One recent mechanistic study specifically notes that signals such as word length, punctuation density and function-word frequency are readily represented in authorship encoders, which is another reason it's useful to expose those dimensions explicitly rather than asking an embedding to explain itself. [DOI](https://doi.org/10.48550/arXiv.2605.19908?utm_source=chatgpt.com)

I'd additionally keep character 3–5 gram TF-IDF + linear SVM as a boring baseline. Authorship is one of those areas where “boring” character features remain annoyingly powerful.

5. **Put the forest/GBM above comparisons, not raw embeddings.** This is where I'd modify your forest idea slightly.

I wouldn't do:

```text
512 embedding dims
      ↓
RandomForest
```

with a sparse positive dataset. It will find all kinds of dubious boundaries.

I'd do:

```text
LUAR similarities       ~20 features
CISR similarities       ~10
ModernBERT PLI          ~10
stylometric distances   ~50–200
char-ngram margin        ~5
semantic similarity      ~5
length/coverage          ~5
                           ↓
                  LightGBM / CatBoost
```

My likely leaderboard would be:

```text
Calibrated logistic regression   ← sanity baseline
LightGBM                         ← likely production choice
CatBoost                         ← benchmark
ExtraTrees                       ← useful alternate
RandomForest                     ← benchmark
```

Gradient boosting is generally a nicer match than a classic RF for heterogeneous feature groups and smallish tabular datasets.

Crucially, the model's unit of validation must still be the **document**, not the chunk.

With a sparse initial blog corpus, I'd use leave-one-document-out evaluation:

```text
fold 1: fingerprints from blogs 2–6 → test blog 1
fold 2: fingerprints from blogs 1,3–6 → test blog 2
...
fold 6: fingerprints from blogs 1–5 → test blog 6
```

Never train on chunks from blog #3 and then test on different chunks from blog #3. That will give you spectacularly misleading numbers.

You also need negatives. Ideally, these are pieces by many other people drawn from approximately the same genre. Better still, include **hard negatives**:

```text
other author + same subject
other author + same genre
other author + similar vocabulary
other author + similar sentence length
other author + deliberately similar tone
```

This is how you force the system to learn “you” rather than “person who writes technical blog posts about ML.”

The CISR work specifically demonstrates the underlying problem: conventional authorship training can encode topic/content rather than pure style unless the training design controls for it. [ACL Anthology](https://aclanthology.org/2022.repl4nlp-1.26/?utm_source=chatgpt.com)

6. **Do not fine-tune the transformer on a sparse dataset yet.** This would be one of my stronger recommendations.

You have an extremely good few-shot setup for:

```text
frozen strong authorship encoder
          +
personal reference bank
          +
small learned verifier
```

You do *not* yet have enough independent positive examples to convince me that LoRA/fine-tuning a 600M encoder toward your identity is doing anything except memorization.

If you find 30–100 genuinely separate pieces of historical writing, that calculation starts changing. At that point I'd test contrastive adaptation using:

```text
positive pair:
your document A / your document B
with deliberately different topics

negative pair:
your document / another author's document
with deliberately similar topics
```

That is exactly the direction the authorship-representation literature has found useful: content-controlled contrastive learning. [ACL Anthology](https://aclanthology.org/2021.emnlp-main.70/?utm_source=chatgpt.com)

Your 80 GB RAM is vastly more than necessary for inference on these models. The new LUAR-MV-Qwen is only 0.6B parameters. GPU VRAM will matter much more for training throughput; CPU + 80 GB will still let you run the entire pipeline, just considerably slower. [Hugging Face](https://huggingface.co/rrivera1849/LUAR-MUD-MV-Qwen?utm_source=chatgpt.com)

The explainer is where I think this project can become unusually good.

I would produce **three independent kinds of explanation**, rather than trying to translate transformer dimensions into English.

First, an interpretable statistical deviation report:

```text
Sentence length:
    you:       median 21.4 words
    candidate: median 12.1 words
    deviation: -1.9σ

Semicolon rate:
    you:       2.8 / 1,000 words
    candidate: 0.0 / 1,000
    deviation: -1.6σ

Contractions:
    you:       7.1 / 1,000
    candidate: 1.3 / 1,000
    deviation: -2.2σ

1st-person singular:
    within normal range

Paragraph length:
    candidate significantly shorter than reference distribution
```

TreeSHAP works beautifully here because the features have actual linguistic meanings.

Second, do **sentence-level deletion attribution**.

For every sentence \(s_i\):

\[
\Delta_i =
S(T\setminus s_i)-S(T)
\]

If removing sentence 17 raises the fingerprint score from .68 to .81, that sentence is probably stylistically anomalous.

That gives you reports like:

```text
Most style-inconsistent passages

#1 sentence 17       Δmatch = +0.13
#2 sentences 22–24   Δmatch = +0.08
#3 sentence 4        Δmatch = +0.05
```

This is far more defensible than asking SHAP to explain 512 latent dimensions.

Third, retrieve **reference analogues**:

```text
Candidate:
"Anyway, the weird thing about this architecture is..."

Closest passages from your historical writing:
Blog 4 ¶12    similarity .84
Blog 1 ¶7     similarity .81
Blog 6 ¶18    similarity .79
```

And for anomalous passages:

```text
This paragraph is unlike every reference segment:
max similarity = .39
```

Then explain its measurable properties.

Your eventual API could therefore be something like:

```python
report = fingerprint.score(text)

report.match_score
# 0.86

report.confidence
# "high"

report.embedding_score
# 0.89

report.stylometry_score
# 0.81

report.char_ngram_score
# 0.84

report.topic_similarity
# 0.27

report.anomalous_sentences
# [...]

report.feature_deviations
# [...]

report.nearest_reference_passages
# [...]

report.explanation()
```

And human-readable output could be:

```text
STYLE MATCH: 86 / 100
Confidence: HIGH
Text length: sufficient

The text is strongly compatible with your historical writing.

Strong matches:
• Function-word usage is very close to your baseline.
• Parenthetical frequency is characteristic.
• Sentence-length variance closely matches your reference corpus.
• Authorship embeddings match most historical documents strongly.

Largest mismatches:
• Paragraphs are ~31% shorter than your historical norm.
• Passive constructions are 2.1 SD above your baseline.
• Semicolon usage is unusually low.
• Sentences 14–16 account for most of the embedding mismatch.

Sentence 15:
    Removing this sentence raises the overall score
    from 0.86 → 0.90.

    Likely reasons:
    - unusually terse
    - atypically formal vocabulary
    - low function-word similarity
    - syntax differs from historical distribution

Closest historical analogue:
    blog_2018_04.txt, paragraph 7
    style similarity: 0.88
```

One other thing I'd explicitly add is an **uncertainty model**.

I would not tell you:

```text
P(you wrote this) = 97.438%
```

unless we've built a legitimate population/calibration model.

Instead:

```text
Style compatibility: 91/100
Evidence strength: high
Calibration region: well represented
```

For 50 words:

```text
Style compatibility: 82/100
Evidence strength: low
Reason: insufficient text for stable fingerprint
```

Once we have a good negative population, we can calibrate this into something more probabilistic using held-out authors and Platt/beta calibration.

For evaluation I'd care about **AUROC, EER, TPR at low false-positive rates, Brier/calibration error**, and—most importantly—performance under intentionally topic-mismatched conditions. Plain accuracy is almost irrelevant.

If I were implementing version 1 today, my exact stack would therefore be:

```text
                  ┌ LUAR-MUD-MV-Qwen
candidate ────────┼ CISR
                  ├ char 3–5gram SVM
                  ├ stylometry
                  └ semantic embedding (nuisance/control)
                           │
                           ▼
               pairwise/reference features
                           │
                      LightGBM
                           │
                    sigmoid calibration
                           │
                 compatibility score
                           │
       ┌───────────────────┴────────────────────┐
       ▼                                        ▼
 TreeSHAP/stylometry                    sentence deletion
 feature explanation                    + reference retrieval
```

And I'd regard **LUAR multi-vector + stylometry + char n-grams + LightGBM** as the core experiment. CISR/ModernBERT late interaction become ablations to determine whether they improve your actual held-out-document performance.

The fact that TinyStyler successfully uses pretrained authorship representations for few-shot imitation is also encouraging for this general setup: style embeddings demonstrably retain useful author-specific information from small reference sets. [ACL Anthology](https://aclanthology.org/2024.findings-emnlp.781/?utm_source=chatgpt.com)

The single biggest determinant of how good this becomes probably won't be your 80 GB of RAM. It'll be **finding more genuinely independent pre-AI samples of your writing and assembling a nasty, topic-matched negative corpus**. Once those exist, this becomes a very nice ML problem rather than a six-sample overfitting problem.

# Addendum — MVP Implementation Constraints and Final Architecture Decisions

This addendum is part of the existing **Personal Writing Style Fingerprint MVP PRD** and overrides any conflicting implementation choices in the earlier sections.

There is only **one MVP PRD**. Do not split this work into separate PRDs or phases.

## 1. Guiding Principle

Build the smallest maintainable system that provides:

1. a strong personal writing-style fingerprint,
2. a useful 0–100 compatibility score,
3. explanations of stylistic matches and mismatches,
4. passage-level anomaly detection,
5. reliable document-level evaluation.

Prefer a simple, understandable implementation over marginal accuracy gains requiring substantially more models, abstractions, infrastructure, or dependencies.

The expected user is technical and will primarily use the Python API and CLI locally.

---

## 2. Final MVP Architecture

The MVP will use exactly three style signals:

```text
LUAR-style authorship embeddings
            +
interpretable stylometric features
            +
character n-gram similarity
            ↓
     small tabular verifier
            ↓
  compatibility score + explanation
```

Do not add additional transformer ensembles, multiple authorship encoders, deep late-interaction architectures beyond the chosen authorship encoder, neural classifiers, LLM-based judges, vector databases, services, queues, APIs, databases, or distributed infrastructure.

### Authorship embeddings

Use one pretrained authorship-oriented embedding model with passage-level embeddings.

Use the current LUAR multi-vector/Qwen checkpoint selected in the main PRD unless it is technically unusable in the target environment. Do not introduce a second authorship encoder in the MVP.

Historical passages remain individually represented. Do not collapse the entire corpus into one embedding.

Candidate/reference comparison uses symmetric MaxSim-style cosine similarity as previously defined.

### Stylometry

Implement a focused set of approximately **50–100 stable, interpretable features**, not hundreds merely because they are possible.

Prioritize:

- sentence length and variance,
- paragraph length,
- word length,
- lexical density,
- contractions,
- pronouns,
- function words,
- punctuation,
- headings/lists,
- rhetorical questions,
- parentheticals,
- transition words,
- basic POS distributions where available.

Do not build a large NLP feature framework.

### Character fingerprint

Use character 3–5 gram TF-IDF.

Use cosine similarity against historical passages/profile as the primary char-level signal.

Do not train a standalone SVM unless a real negative-author corpus exists.

### Final verifier

When adequate negative samples exist, use **LightGBM** over derived comparison features.

Also train logistic regression as the simple baseline for evaluation.

Choose LightGBM only if grouped validation demonstrates a meaningful improvement over logistic regression.

Without negative data, do not pretend there is enough supervised data to train a binary verifier. Produce the score from normalized reference similarity components instead.

This behavior must be automatic.

---

## 3. Remove Semantic Embedding Model From MVP

Do not include a separate general-purpose semantic embedding model in the MVP.

It adds another model, more dependencies, more inference, more artifact management, and insufficient immediate value relative to the corpus size.

Topic leakage should instead be controlled primarily through:

- document-level validation,
- hard negative samples when available,
- character/stylometric disagreement,
- evaluation using writing on differing topics.

Semantic-control embeddings may be added later only if empirical evaluation demonstrates a real need.

Tests may mirror these modules.

Do not create one Python module per small concept.

Do not introduce:

- plugin systems,
- registries,
- abstract base classes for single implementations,
- factories with only one implementation,
- service layers,
- event systems,
- custom serialization frameworks.

Use plain Python functions and small dataclasses unless abstraction clearly reduces complexity.

All implementation must follow **red → green → refactor**.

Before implementing production functionality:

1. write all BDD-style tests for the intended observable behavior,
2. run them,
3. verify that the new tests fail for the expected reason,
4. investigate any test that unexpectedly passes,
5. only then implement production code,
6. make the complete test suite green,

## 9. Corpus Processing Decisions

Markdown discovery:

```text
blog_posts/**/*.md
```

Treat each file as one independent document.

Cleaning removes:

- YAML front matter,
- fenced code,
- inline code,
- HTML markup,
- images,
- bare URLs.

Preserve ordinary prose structure and punctuation.

Chunk by paragraphs.

Target roughly:

```text
200–400 words
```

Merge adjacent paragraphs until the target size is reached.

Do not create overlapping windows by default.

Chunks below 100 words should be merged with an adjacent chunk when possible.

No sophisticated semantic chunker is required.

## 10. Reference Representation

Persist every historical passage independently.

Conceptually:

```python
ReferencePassage(
    document_id="post_1.md",
    passage_id=3,
    text="...",
    embedding=array(...),
    stylometry={...},
)
```

A user's style fingerprint is the **distribution of reference passages and features**, not one universal average vector.

Document identity must remain attached to every passage.

---

## 11. Scoring

For a candidate:

1. clean it using the same pipeline as historical prose,
2. split it using the same chunker,
3. embed candidate chunks,
4. compare them with historical chunks,
5. calculate stylometric differences,
6. calculate char n-gram similarity,
7. create the final compatibility score,
8. calculate evidence strength,
9. generate explanations.

The public score is always:

```text
0–100 style compatibility
```

It must never be labeled an authorship probability in the MVP.

---

## 12. Unsupervised Score Without Negative Corpus

Because the initial repository may contain only the user's positive examples, the default MVP must work without fabricated negatives.

Normalize each signal against leave-one-document-out historical behavior.

For example:

```text
embedding compatibility
stylometric compatibility
char compatibility
```

Convert each into a robust historical percentile or normalized similarity.

Combine them using fixed weights initially:

```text
embedding: 0.60
stylometry: 0.25
character: 0.15
```

These values are the MVP defaults.

Do not expose them as tunable complexity unless needed.

If validation later demonstrates a clearly better fixed weighting, update the configuration and document why.

---

## 13. Supervised Mode With Negative Corpus

If `negative_posts/` exists and contains sufficient independent documents, train the supervised verifier.

Minimum:

```text
10 independent negative documents
from at least 3 distinct authors where author identity is available
```

If this threshold is not met, stay in reference-similarity mode.

Use derived comparison features only.

Do not feed raw transformer dimensions into LightGBM.

Select between logistic regression and LightGBM using grouped validation.

LightGBM must exceed logistic regression by at least a modest predefined margin on the primary validation metric to justify the additional complexity.

Default margin:

```text
AUROC improvement >= 0.02
```

Otherwise use logistic regression.

---

## 14. Explanation Design

Keep explanation deterministic and evidence-based.

No LLM is required for explanations.

The explanation consists of:

1. stylometric deviations,
2. component-level score contributions,
3. anomalous passages/sentences,
4. closest historical passages.

### Feature explanations

Report the largest absolute robust deviations that are also meaningful enough to communicate.

Example:

```text
Paragraph length
Historical median: 104 words
Candidate median: 61 words
Candidate is substantially shorter than normal.
```

Do not report dozens of trivial features.

Default:

```text
5 strongest matches
5 largest mismatches
```

### Tree/model explanations

If LightGBM is selected, use SHAP for top-level derived features.

If logistic regression is selected, use signed standardized feature contributions.

Do not add SHAP merely when it is unnecessary.

---

## 15. Anomaly Analysis

Do not exhaustively delete every sentence from every long document.

Use a two-stage process:

1. score candidate passages individually,
2. identify the lowest-scoring passages,
3. perform sentence-deletion analysis only inside the worst passages.

Default:

```text
inspect at most 3 suspicious passages
inspect at most 20 sentences total
```

This keeps explanation cost bounded while preserving useful diagnostics.

---

## 16. Historical Passage Retrieval

Do not introduce FAISS or another vector database for a small blog corpus.

Use NumPy cosine similarity directly against persisted embeddings.

A vector database becomes justified only when the reference corpus becomes orders of magnitude larger.

Return the top three historical analogues by default.

## 17. Evidence Strength

Evidence strength is deterministic.

Default rules:

```text
LOW:
< 150 usable words

MEDIUM:
150–499 usable words

HIGH:
>= 500 usable words
```

Downgrade one level when the candidate has extreme disagreement between component signals.

Do not use vague learned confidence until sufficient calibration data exists.

```bash
python -m style_fingerprint build
python -m style_fingerprint score FILE
python -m style_fingerprint explain FILE
python -m style_fingerprint evaluate
```

`score` provides a compact result.

`explain` provides the full diagnostic output.

Do not add an interactive shell, server, UI, daemon, or configuration wizard.

---

## 21. Configuration

Configuration belongs in one small dataclass or module.

Environment variables are unnecessary unless required for model-cache locations.

CLI flags should only exist for options users plausibly need.

Do not make every internal constant configurable.

Important fixed MVP defaults should remain in code with clear names.

---

## 22. Failure Behavior

Fail loudly and clearly when:

- no Markdown posts exist,
- a document contains no usable prose,
- the embedding model cannot load,
- saved artifacts are incompatible with the current feature/model schema,
- scoring input contains insufficient usable text to calculate any meaningful signal.

Warnings rather than failures should cover:

- small historical corpus,
- no negative corpus,
- short candidate text,
- weak disagreement-based evidence.

Never silently fall back to a materially different embedding model.

Update `README.md` as part of the same implementation.

- what the tool measures,
- what the 0–100 score means,
- what it does **not** mean,
- installation,
- `blog_posts/` input expectations,
- build command,
- score/explain commands,
- Python API,
- how explanations work,
- how to add additional historical posts,
- optional `negative_posts/`,
- rebuild/cache behavior,
- major limitations.

Document that more independent historical documents improve reliability more than generating more chunks from the same document.

Document that the system measures compatibility with the supplied historical writing style and is not forensic proof of authorship.

Before completion:

- `prototype/` is ignored and untracked,

## 25. Explicit Non-Requirements

Do not implement in the MVP:

- web application,
- REST API,
- database,
- Docker unless the repository already requires it,
- GPU-specific code paths beyond normal library device selection,
- semantic embedding control model,
- multiple authorship encoders,
- transformer fine-tuning,
- LoRA,
- custom neural network verifier,
- FAISS/vector DB,
- LLM-generated explanations,
- AI-writing detection,
- automatic web scraping of negative authors,
- style rewriting,
- live model monitoring,
- experiment-tracking infrastructure,
- distributed processing.

## 26. Definition of Done

The MVP is complete when:

1. all required BDD tests were written before production implementation and were observed failing for the expected reasons;
2. all tests are green;
3. Markdown files from `blog_posts/` can produce a reusable fingerprint;
4. unchanged expensive embeddings are cached;
5. arbitrary prose can be scored from CLI and Python;
6. results contain a 0–100 compatibility score and deterministic evidence strength;
7. explanations identify strongest matches, largest mismatches, anomalous passages, and historical analogues;
8. leave-one-document-out evaluation proves there is no same-document leakage;
9. the tool operates correctly with no negative corpus;
10. supervised calibration activates only when sufficient negative data exists;
11. the codebase follows the intentionally small architecture above;
12. `prototype/` is never committed or used as runtime production code;
13. README documentation reflects the implemented behavior;
14. the complete default test suite runs locally without requiring expensive real-model inference;
15. a separately marked smoke/integration test verifies the real embedding pipeline.

The implementation should stop here. Additional architecture or capabilities require demonstrated need rather than anticipation of possible future requirements.

The main simplification is that the MVP now has one authorship encoder, one compact stylometry implementation, one char-level signal, and only introduces supervised boosting when the data actually supports it. That keeps the accuracy-oriented parts of the original design without turning a small blog corpus into an ML platform.
